# TDD: 빨강 → 초록 → 리팩터링

이 저장소의 테스트는 `node --test`(`tests/*.test.mjs`, `node:test` + `node:assert/strict`)로 돌린다. 세 단계를 순서대로 밟고, 단계를 건너뛰지 않는다. 각 단계가 끝날 때마다 사용자에게 무엇을 했고 테스트 결과가 어땠는지 한두 줄로 알린다.

## 0. 무엇을 고칠지 정한다
- 고칠 동작을 한 문장으로 적는다(예: "ㄱㄴ을 치면 강남이 맨 위에 나온다"). 이 문장이 테스트 이름이 된다.
- 고칠 모듈과 그 모듈의 테스트 파일을 찾는다(`stats.mjs` → `tests/stats.test.mjs`처럼 이름이 대응한다). 없으면 같은 이름으로 새로 만든다.
- 동작이 모호하면 테스트를 쓰기 전에 사용자에게 묻는다.

## 1. 빨강: 실패하는 테스트를 쓴다
- 제품 코드는 아직 건드리지 않는다. 테스트 파일만 고친다.
- 테스트 이름은 한국어로, 기대하는 동작을 그대로 쓴다. 주변 테스트의 모양(가져오기, 도움 함수, `assert.equal`/`assert.deepEqual`/`assert.ok`)을 따른다.
- 시간대·필드는 공통 규칙을 따른다: 시간대 순서는 `HOURS`, 필드는 `stats.mjs`의 `count`로 읽고 키 문자열을 직접 만들지 않는다.
- 실제 데이터 파일에 기대는 테스트라면 `tests/CLAUDE.md`의 기대값과 어긋나지 않는지 본다.
- 새 테스트만 돌려 **실패하는 것을 눈으로 확인**한다.
  ```sh
  node --test --test-name-pattern="<테스트 이름 일부>" tests/<파일>.test.mjs
  ```
- 실패 까닭이 맞는지 본다. 기대값이 달라서(assertion) 실패해야 한다. 가져오기 오류·오타·문법 오류로 실패했다면 테스트를 먼저 바로잡고 다시 돌린다.
- 처음부터 통과한다면 이미 되는 동작이거나 테스트가 잘못된 것이다. 멈추고 어느 쪽인지 사용자에게 알린다.

## 2. 초록: 최소한으로 통과시킨다
- 방금 쓴 테스트를 통과시키는 데 필요한 만큼만 제품 코드를 고친다. 테스트를 고쳐서 통과시키지 않는다.
- 요청에 없는 기능·정리는 이 단계에서 하지 않는다.
- 새 테스트를 다시 돌려 통과를 확인하고, 이어서 전체를 돌린다.
  ```sh
  npm test
  ```
- 다른 테스트가 깨졌으면 먼저 그것을 고친다. 깨진 테스트를 지우거나 기대값을 바꿔 덮지 않는다(기대값이 정말 바뀌어야 한다면 까닭을 사용자에게 말하고 확인받는다).

## 3. 리팩터링: 초록을 유지하며 다듬는다
- 동작은 그대로 두고 중복 제거, 이름 다듬기, 공용 모듈(`stats.mjs` 등) 재사용처럼 구조만 고친다. 테스트 코드도 다듬어도 된다.
- 한 번에 작게 바꾸고, 바꿀 때마다 `npm test`를 돌린다. 빨강이 되면 방금 바꾼 것을 되돌린다.
- 다듬을 것이 없으면 "리팩터링할 것 없음"이라고 말하고 넘어간다.
- 주변 코드의 주석 밀도·이름 짓기·말투를 따르고, 주석은 한국어로 쓴다.

## 4. 마무리
- 마지막으로 `npm test` 전체 결과(통과/실패 개수)를 보고한다. 실패가 남았다면 숨기지 않고 출력과 함께 알린다.
- 화면(`*.html`)에 영향이 있으면 테스트로 확인되지 않는 부분을 따로 적는다.
- 커밋은 사용자가 요청할 때만 한다.
