- 측정 대상: `frame-map.json`에 있는 화면 프레임만. A의 Components 프레임, B의 Design System·Handoff 페이지는 빠져 있다.

## 하네스에 불리한 결과

1. **시간·비용이 크게 늘었다.** 에이전트 작업 시간 3.1분 → 17.9분(5.8배), 비용 $1.41 → $7.86(5.6배), 토큰 129만 → 1,048만(8.1배), 턴 17 → 37.
   - 17.9분은 `result.duration_ms`를 더한 값이고, 사람이 승인하는 동안 기다린 시간은 넣지 않았다. 벽시계로는 A가 01:09:18–01:12:28(약 3분), B가 01:09:20–01:34:35(약 25분)다.
   - B는 운영자 입력이 5번 더 필요했다(prompt-2~6). 사람 손이 가는 횟수도 비용에 넣어야 한다.
2. **독립 비평 점수는 사실상 같다.** 새 맥락 비평 에이전트가 같은 지시로 매긴 점수가 A 11/20, B 12/20로 1점 차이다. 수치 지표 차이만큼 화면 품질 차이가 나지는 않았다.
   - 두 실행 모두 같은 High 문제가 남았다: 데이터 기준 시각이 없음(A는 상세 화면만, B는 모든 화면). 1대 남은 대여소가 넉넉한 곳과 같은 초록으로 보임(A High, B Medium). 행을 누를 수 있다는 표시가 없음.
   - B에서만 나온 지적: 빈 상태가 에러 상태와 구분되지 않음, 0대 대여소의 상세 화면이 없음, 위·경도 소수점 8자리를 그대로 보여 줌, '거치대 15'에 단위가 없음, 출처 문구가 단어 중간에서 줄바꿈됨.
3. **하네스 안의 자체 비평이 점수를 후하게 줬다.** 하네스의 design-critic(`review-in-harness.json`)은 B에 17/20을 줬다. 같은 화면을 독립 비평은 12/20으로 봤다. real-world·consistency·control·tone·brand 다섯 항목에서 1점씩 더 줬다. 이 차이에는 copy.json·wireframes.json을 볼 수 있었던 영향도 있지만, 독립 비평이 지적한 단위 누락과 원시 좌표 노출을 자체 비평은 "문제없음"으로 넘겼다.
4. **B는 끝까지 통과하지 못했다.** 마지막 `npm run check`가 `figma FAIL(내보내기 오래됨)`으로 끝났다. 다시 내보내던 중에 Figma MCP Starter 요금제 호출 한도에 걸렸다. `run-b/nodes.json`은 01:26:17에 내보낸 것이고, 마지막 Figma 수정은 01:30:26이다.
   - 그 뒤 수정은 Design System·Handoff 페이지의 글자 노드 2개(4:172, 4:186)뿐이었다(session-6의 use_figma 코드로 확인). 그래서 화면 프레임 지표에는 영향이 없을 것으로 본다. 다만 다시 내보내서 확인하지는 못했다.
   - 같은 내보내기 오래됨 FAIL이 `failures.jsonl`에 7번 쌓였다.
5. **B 첫 Figma 빌드가 하네스 기준을 못 맞췄다.** 기준 서체 Pretendard가 파일에 없어서 글자 39개가 모두 Noto Sans KR로 들어갔고, 린트 오류 39개가 났다. 사람이 기준 서체를 바꾸고 system을 다시 승인해야 했다.
6. **화면마다 높이가 다른 컴포넌트가 B에서만 1개 나왔다.** StateMessage가 loading 88 / empty 148 / error 196px다. 내용(버튼 유무)이 달라서 생긴 차이라 실제 결함인지는 사람이 판단해야 한다. 그래도 지표상으로는 B가 나쁘다.

## B에 유리하게 나온 지표를 읽을 때 주의할 점

- **터치 영역 미달 A 3건은 오탐이다.** 레이어 이름 휴리스틱(`row` 포함)이 상세 화면의 정보 행 `Row/위도`·`Row/경도`·`Row/대여소 ID`(318×20)를 누르는 요소로 잡았다. 실제로 누르는 요소에서 나온 미달은 A도 0건이다.
- **명도 대비 미달 A 24건 중 11건은 기준에 조금 못 미친 값이다**(4.18–4.35:1. 기준은 4.5:1). 크게 모자란 것은 `#8B95A1 on #F9FAFB`(2.91:1, 11px) 8건, 흰 글자 on 초록 버튼(3.39:1) 2건 등이다.
- **"변수에 안 묶인 색 비율"과 "서로 다른 값 수"는 하네스가 강제하는 항목이다.** A는 처음부터 토큰이 없었으니 1(100%)인 것이 당연하다. 값 수(색 13 vs 7, 글자 크기 13 vs 4 등)는 일관성을 보여 주는 대리 지표일 뿐이고 화면 품질 자체는 아니다.
- **빠진 상태 A 1개(list/loading)는 A 프롬프트에 상태 요구가 없었던 영향이 있다.** A는 "화면 3~4개"를 화면 4개로 그렸다. B는 하네스가 상태를 요구한다.
- **화면마다 높이가 다른 컴포넌트 A 0은 비교 대상이 적어서다.** A의 인스턴스는 11개(StationRow·SourceFooter·Button)다. B는 30개다.

## 실험 조건이 B에 유리하게 바뀐 점

- **실행 중에 하네스를 고쳤다**(`approvals.log` 01:15:22, 01:15:44): 노드 내보내기 페이지 나눔, 화면별 states 허용, compact paint, 짧은 영역 SVG 글자 넘침. 그래서 B는 실험 시작 때의 하네스가 아니라 도중에 고친 하네스로 끝났다. A에는 이런 개입이 없었다.
- **승인은 단테가 아니라 실험 운영자(에이전트)가 했다**(`approvals.json`의 by). 와이어프레임 질문 4개에 대한 답(prompt-2)과 승인 메모(출처 위치, 로딩 문구, 0대 빨강)도 운영자가 줬다. 이 입력이 B 결과에 반영됐다.
- **노드 내보내기 설정이 프로토콜과 다르다.** 프로토콜은 두 파일 모두 `ONLY_SCREEN_FRAMES=false`로 내보내라고 했다. A는 그대로 했지만, B의 `nodes.json`은 하네스가 실행 중에 `ONLY_SCREEN_FRAMES=true`, `PAGE_NAME="Screens"`로 내보낸 것이다. frame-map이 같은 화면 프레임만 고르니 수치에는 영향이 없을 것으로 보지만, 같은 절차는 아니다.
- **B는 Opus와 Sonnet을 함께 썼다**(서브에이전트). A는 Opus만 썼다.
- 측정에 든 비용은 표에 넣지 않았다: A 노드 내보내기 $0.58, A 비평 $0.66, B 비평 $0.64.

## 요약

자동 지표(값 개수, 대비, 토큰 바인딩, 상태 누락)는 B가 확실히 좋다. 하지만 그중 일부는 하네스가 강제하는 항목이거나 오탐이다. 독립 비평 점수는 11 vs 12로 차이가 거의 없다. 비용·시간은 5~6배 들었고, 사람 개입은 5번 늘었고, 마지막 검증도 통과하지 못했다. 사람 점수가 들어오기 전까지 "하네스가 더 좋은 디자인을 만든다"고 결론 내릴 근거는 약하다.
